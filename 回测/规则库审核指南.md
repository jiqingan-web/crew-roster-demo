## 1. 系统总览

**这是什么**：成都航空 A320 机队（含 C909 中队）三人制飞行机组的月度排班与合规校验引擎。它有两个用途：

- **自动排班（求解器）**：给每个任务挑人，候选人必须通过 `personCheck`（个人能不能飞）和 `crewIssue`（三个人能不能一起飞）。
- **事后校验（`validate`）**：对一份已有班表（系统排的或导入的真实班表）输出违规清单，分三级：
  - `hard`：硬违规，不允许
  - `soft`：软提示，合规或待确认，需要提醒
  - `info`：信息，只做展示

**规则在哪里**

| 位置 | 内容 |
|---|---|
| `rules/crew_rules.yaml` | 搭配矩阵、特殊/高原机场、年龄、模拟机、FDP 窗口等配置（RE12 + 运行手册第 17 章） |
| `js/rules-config.js` | 由 `python3 scripts/gen_rules_config.py` 从 YAML 生成，不要手改 |
| `js/core.js`（约 5200 行） | 全部判定逻辑和默认参数（`defaultSettings`，约第 224 行） |
| `rules/import_spec.yaml` | 班表导入字段规范 |
| `ref/RULES_BLUEPRINT_121_COM.md` | 2026-11-03 的规则分层蓝图（**部分内容已过期**，见 §7） |
| `ref/SELF_AUDIT_v6xx_*.md` | 历次单项改动的自审记录 |
| `回测/全年真实班表回测报告.md` | 14 轮全年回测记录，每轮说明改了什么、数字怎么变 |

**依据层级（冲突时上层优先，下层只能更严，放宽必须明确标注）**

1. **121**：CCAR-121-R8 P 章（121.481–121.495），法规底线
2. **COM**：《公司运行手册》3.6 章（Re07-10）、第 17 章（高原/特殊机场）
3. **FD**：《飞行部手册》Re10-08 第 2.2 节（报到、休息期、疲劳管理）
4. **RE12**：《飞行部空客机型操作及搭配上座规定》（2026-09-11）
5. **公司表格**：特殊机场资质表、机场基础表（报到时间/车程）
6. **排班员口径**：用户口头确认的做法，代码注释里写成「用户 2026-11-0x」

> 手册原文不在包内（内部资料）。代码注释里引用的条款号（如 `121.495(b)`、`Re10-08 2.2.4 2)(4)`）是审核时核对的锚点。缺原文时，把判断标为「需对照原文」，不要猜。

**审核要点**

1. **同一套标准是否一致**：`crewIssue` 同时被求解器和 `validate` 调用。`validate` 把「特殊机场授权/搭配」「新机长无教员」降为软，然后用 `_skipAuth/_skipNewCapt` 再查一次其余硬规则。核实：再查一次会不会漏掉第一次被遮蔽的其他硬规则？
2. **机长A/B 的定义来源**：`RANK_ALIAS` 把 A/B 当 J0 查巡航矩阵，`CAPT_AB_MIN_FO` 又覆盖成 F5/F6。核实哪个先生效（`seatOK` 里 `CAPT_AB_MIN_FO` 先返回）。CR-23 把机长B 一律当部门管控人员，这个前提需要书面确认。
3. **放宽项**：CR-19、CR-20、特殊机场资质这三项在校验里都是软。理由是「资质表待更新、导入班表的座位是推断出来的」。核实系统自己排出的班表是否仍按硬标准拦截。
4. **纯置位跳过 FO 矩阵**：置位人员以乘客身份乘机，不上座，逻辑上合理。代码用 `p.legs.some(l => !l.dh)` 判断：只要有一段执飞就照查矩阵。核实混合任务（置位 + 执飞）不受影响。

## 3. 区块 B：报到时间与休息期起止

**代码**：`carOf / repAt / repMinOf / preAt / preCommuteOf / relAt / dutyIvs / report / release`（约 1281–1340 行），`defaultSettings`（约 224 行），`settings.airportTimes`

| 项 | 现行口径 | 依据 |
|---|---|---|
| 国内报到 | 105 分钟 = 地面准备 20 + 车程 25 + 机上 60（成都） | FD 2.2.3；运控现行（用户确认） |
| 国际报到 | 125 分钟（再加 20） | FD 2.2.3 |
| 置位接执飞（首段置位） | 置位前 95 分钟 = 10 + 25 + 60（`dhMergedReportMin`） | FD 2.2.3 5)(3) |
| 纯置位任务 | 登机前 45 分钟（`dhBoardMin`） | FD |
| 休息期开始 | 关车 + 离场 15 + 车程（成都合计 40） | COM 3.6 / FD 2.2.4 |
| 休息期结束 | 基地：下次报到前 25 分钟；外站：报到即止（报到已含车程） | 同上 |
| 最短休息 | **10h**（以前是 12h，手册无依据，已改回） | 121.495(d)、COM 3.6.10 |
| 机场基础表 | 有表的机场按表取报到、航前车程、离场、航后车程；无表的机场按默认值 | 公司机场基础表 |

**审核要点**

1. **起止点**：手工推算几个例子。双流落地 → 双流起飞最少间隔 12h50（40 + 10h + 25 + 105）；天府航前、航后车程都是 0，所以是 12h00。`test/airporttimes.test.js` 覆盖了这两个边界。
2. **默认值不一致**：`repAt` 的兜底是 `S.reportMin || 60`，`fdpDaysRaw` 的是 `releaseMin || 30`，`relAt` 的是 `releaseMin || 40`。设置缺失时口径会不一致。核实迁移逻辑（约 255 行）能否保证这些字段一定存在。
3. **没有数据的外站**：车程默认 25 分钟（与成都相同）。核实这样是否偏宽松：车程实际更长的机场会让休息期被算长。
4. **FDP 计算起点与休息计算起点是否一致**：`report()` 对首段置位的任务用「置位前 95 分钟」，但 FDP 限制计算 `fdpDaysRaw` 用的 `repMinOf` 取的是首个**执飞**段。见 §5 第 1 条。

| 日飞行时间 | 表 A（8h/9h） | 硬 | 121.483(a) |
| 144h 内连续 48h 休息 | 每个飞行任务和主备份之前都要有；**纯置位任务不查** | 硬 | 121.495、COM 3.6.10、FD 2.2.4 2)(4) |

| 月飞行时间 | ≤100h（取个人体检上限和公司上限中较严的一个） | 硬 | 121.483 |
| 年飞行时间 | ≤900h（需要 `ytdFlightH`） | 硬 | 121.483 |
| 第 5 日执飞 / 置位 | 软提示（2026-11-02 起） | 软 | 121.495(b) 原文是禁止，**属于已知软化** |
| 48h 偏紧 | `softRest48H` 默认 48，等于不提示 | — | 取消 60h 软目标 |
| 请假冲突 | 只看有航段起飞的日子和多日任务的中间日；跨午夜落地、航后置位不算占用次日 | 硬 | 用户 2026-11-04 |

**审核要点**

1. **时间窗口的边界**：144h 窗口是 `[报到 − 144h, 报到)`。两个夜间要求的是 `d*DAY+360 ≤ b`，即完整的 00:00–06:00。用刚好卡边界的例子测（休息恰好 48h、恰好从 00:00 开始）。
2. **违规记在哪个任务上**：7 日窗口违规记在窗口内最后一个任务上（`filter(...).pop()`）。核实这是否就是「导致超限的任务」。
3. **月 FDP 分开统计**：跨月任务的 FDP 按日归属。核实跨午夜的那一天归哪个月。
4. **第 5 日软化**：121.495(b) 原文是「不得安排飞行任务」。这是用户拍板的软化，审核时单独列出，交给决策人确认。

## 5. 区块 D：置位、跨午夜与执勤期拆分（豁免最集中，重点审）

**代码**：`dhAdjacentRest`（约 1326 行）、`personCheck` 休息判断段落、`dutyIvs`、`fdpDaysRaw`、`shouldSplitFdpBetween`、YAML `fdp_long_ground_split` / `fdp_window`

| 豁免/口径 | 现行做法 | 依据 |
|---|---|---|
| 航后置位 | 置位任务从前一任务的落地站出发 → 两者之间不要求休息期 | COM 3.7.6 注 2(8) |
| 首日仅置位 | 后一任务第一天只有置位、之后才执飞 → 不受 10h 约束（返回 `'post'`） | FD 2.2.4 2)(4) |
| 航前置位 | 前一任务全是置位且衔接下一任务 → 置位计入后续 FDP，合并后不超限就不报 | COM 3.6.1 3)(1)c |
| 大过站 | 同站衔接、地面 ≥5h、扣除暂停（到位 +30、起飞前 75）后 FDP 未超限 → 软「大过站休息待确认」 | FD 2.2.3 2) |
| 跨午夜往返 | 日期变化但地面间隔 < 长过站门槛 → 不拆成两个执勤期 | 用户确认 |
| 长过站拆分 | 同站地面 ≥5h → 拆成两个 FDP，后段重新报到 | YAML `fdp_long_ground_split` |
| FDP 窗口 | 只从执飞段开始算；两端的置位不延长 FDP | YAML `fdp_window`（2026-11-01） |
| 纯置位任务 | 不查 144h/48h，不查 FO 矩阵 | 121.495(b)、FD 2.2.4 |

**已发现、需要审核方判断的疑点**

1. **置位与 FDP 的口径不统一**：YAML `fdp_window.deadhead_extends_window: false`（置位不计入 FDP），但 COM 3.6.1 3)(1)c 规定「飞前无 10h 休息时，置位时间计入 FDP」。现在**两个独立任务**之间按手册合并（`dhAdjacentRest` → `pre-ok/pre-over`），**同一个任务内**首段置位却不计入 FDP 限制（`fdpDaysRaw` 从首个执飞段起算）。同一个情形在两处口径不同。
2. **「首日仅置位」豁免可能过宽**：返回 `'post'` 后，前一任务与这个任务之间的休息检查**整段跳过**。这个任务第二天执飞前的过夜休息只在 `fdpDays` 里算 `planRestShort`，而那只是 `info` 级（「过夜休息偏短」）。可能的漏洞：前一任务深夜结束 → 次日一早置位 → 第三天执飞，前后两次执飞之间的休息没有被硬检查。请构造用例验证。
3. **多日任务内部的过夜休息只到 info 级**：注释写的是「任务编排数据，需航线部门确认」。从法规看，121.495(d) 对任意两个 FDP 之间都要求 ≥10h。核实这样降级是否合理。
4. **大过站的暂停参数**：+30 / −75 写死在 `personCheck` 里，不在设置或 YAML 里。
5. **请假日判断里写死了 8h**（`480`），和长过站门槛 5h 是两个不同的数。核实两者是否应该统一。

## 8. 审核方法与输出格式

### 8.1 方法

1. **逐条问三个问题**：
   - 依据是什么？对应哪个层级的哪一条？
   - 时间从哪一刻算到哪一刻？边界值（恰好等于）算违规还是合规？
   - 等级对不对？放宽的项有没有依据？
2. **对抗测试**：对 §7 的每一条豁免，构造一个「不应该被豁免」的反例，写成测试（参照 `test/rules.test.js`、`test/fdpsplit.test.js` 的写法，`require('../js/core.js')`）。
3. **检查有没有两套数字**：同一个参数是否同时出现在 YAML、`defaultSettings` 和写死的常量里（已知：`CAPT_AB_MIN_FO`、`NEW_CAPT`、`RANK_ALIAS`、大过站的 30/75、请假的 480、各处兜底默认值）。
4. **求解器与校验是否同标准**：对每条规则核实，求解器的候选过滤（`personCheck` / `crewIssue`）和 `validate` 是否一致；不一致时有没有说明理由。
5. **用剩余违规倒推**：全年回测还剩 17 条硬违规（休息不足 8 条（去重后 4 对）、执勤期超限 3、48h 未含两夜 3、日飞行时间超限 2、144h 1），详见回测报告第十四轮。其中「布努」疑似图卢兹—阿斯塔纳—乌鲁木齐—成都的新飞机接机航班，需要按特殊安排确认。
